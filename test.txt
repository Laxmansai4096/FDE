PART 3: THE FDE ENGINEERING MINDSET: CREATION, INTEGRATION & TESTING
================================================================================

1. HOW THE FDE CONCEIVES & CREATES FEATURES:
   An FDE never builds features without business justification:
   - Business Requirement: Zero customer data leak -> FDE creates LLM Gateway PII scrubbers.
   - Business Requirement: Zero false sales -> FDE creates Hybrid RAG (Vector + SQL Inventory).
   - Business Requirement: Low API bills -> FDE creates Semantic Vector Caching.
   - Business Requirement: Open enterprise integration -> FDE creates Model Context Protocol (MCP).

2. HOW THE FDE TESTS EDGE CASES IN THE BACKEND:
   - Edge Case A: Stale Embeddings -> FDE builds Cache Flush API (POST /api/cache/flush).
   - Edge Case B: Adversarial Attacks -> FDE builds Security Red-Teaming Suite (POST /api/redteam).
   - Edge Case C: Low Retrieval Recall -> FDE builds HyDE & RRF Retriever (POST /api/hyde).
   - Edge Case D: RAG Hallucinations -> FDE builds Ragas Quality Benchmark Evaluator (POST /api/evals).

3. HOW BACKEND INTEGRATION WORKS:
   All services interface through server/index.js:
   Client Prompt -> Azure APIM Rate Limit -> Content Safety -> Gateway Guardrail 
   -> Cache Check (if hit -> return 0ms) -> Hybrid RAG Retrieval -> LLM Generation 
   -> Store Cache -> Telemetry Span Log -> UI Response.
